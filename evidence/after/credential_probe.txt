CREDENTIAL PROBE — variant (b): scoped SAS, independently runnable by a third party
=====================================================================================

Purpose: prove the containment control at the CREDENTIAL layer, not just by
observing that the reader's log says CLOSED. A third party with no lab-internal
access can reconstruct this probe using only the two SAS query strings (which
they can extract if they have any interception point on the sandboxes' env
vars, or — as here — regenerate SAS tokens with identical scope/permissions
against the same containers to confirm the *design*, since the containers'
access policy is what's actually under test).

Run ID under test: 6a50151453977
Storage account:   ccstor3xnygvmi7f3z
Writer container:  wr-6a50151453977  (writer SAS permission: cw = create+write only)
Reader container:  rd-6a50151453977  (reader SAS permission: rl = read+list only)
Probe timestamp (UTC): 2026-09-12T22:30:0{2,3}Z


PROBE 1 — Cross-container: reader's SAS (rl, scoped to rd-<runId>) attempts
LIST on the WRITER's container (wr-<runId>)
-----------------------------------------------------------------------------
Request:
  GET https://ccstor3xnygvmi7f3z.blob.core.windows.net/wr-6a50151453977
      ?restype=container&comp=list&<reader's SAS query string, signed for rd-6a50151453977>

Result: HTTP 403
  <Error>
    <Code>AuthenticationFailed</Code>
    <Message>Server failed to authenticate the request. Signature did not
    match. String to sign used was rl / 2026-09-12T22:59Z /
    /blob/ccstor3xnygvmi7f3z/wr-6a50151453977 / ... </Message>
  </Error>

Interpretation: the reader's SAS signature is cryptographically bound to the
canonicalized resource path of ITS OWN container (rd-<runId>). Reusing it
against a different container path invalidates the signature and the request
is rejected BEFORE authorization is even evaluated. This is a stronger
isolation property than a permission check: the credential does not merely
lack rights elsewhere, it is bound to its own resource by construction.


PROBE 2 — Same-container, wrong permission: writer's SAS (cw, scoped to
wr-<runId>) attempts LIST/READ on its OWN container
-----------------------------------------------------------------------------
Request:
  GET https://ccstor3xnygvmi7f3z.blob.core.windows.net/wr-6a50151453977
      ?restype=container&comp=list&<writer's SAS query string, signed for wr-6a50151453977, perm=cw>

Result: HTTP 403
  <Error>
    <Code>AuthorizationPermissionMismatch</Code>
    <Message>This request is not authorized to perform this operation using
    this permission.</Message>
  </Error>

Interpretation: the writer's SAS authenticates correctly (its signature IS
valid for this container) but is denied at the authorization layer because
its granted permission set (cw = create+write) does not include read or list.
This is the direct least-privilege proof: even within its own scope, the
writer's credential cannot be used as a covert RECEIVE channel.


SUMMARY
-----------------------------------------------------------------------------
- Reader cannot reach writer's namespace at all (signature-bound rejection).
- Writer cannot read/list even its own namespace (permission-bound rejection).
- Combined, neither credential can be used, alone or together, to replicate
  the "before" channel: there is no operation available to either sandbox
  that lets it observe a token placed by the other.

How a third party reproduces this WITHOUT lab access:
  1. Read containment_sas.bicep: confirm writer SAS = {signedResource: c,
     signedPermission: cw, canonicalizedResource: .../wr-<runId>} and reader
     SAS = {signedResource: c, signedPermission: rl, canonicalizedResource:
     .../rd-<runId>} — i.e. disjoint containers, disjoint permissions, by
     inspecting the deployed template/parameters alone.
  2. Independently mint SAS tokens with the SAME declared scope (their own
     test storage account, or if given read access to deployment parameters,
     the exact tokens) and run the two curl requests above. Expect 403 in
     both directions. A different result (200) would falsify the containment
     claim.
